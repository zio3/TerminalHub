# リンクプラグインの書き方

TerminalHub のターミナル出力中の文字列を検出して、クリックできる URL リンクにする仕組み。

このファイルは **LLM に丸ごと渡して `.js` を生成させる** ことを想定して書いてある。
「`ABC-123` を社内 Jira に飛ばしたい」のような要望と一緒に渡せば、動くものが出てくるはず。

> **無保証**: 生成されたプラグインの動作は保証しない。壊れていてもターミナル本体は動く
> （読み込みや検出で例外が出たプラグインは、そのプラグインだけが無効になる）。
> エラーはブラウザの DevTools コンソールに出るので、そこを見て直すこと。

> **このファイルは編集しないこと**: プラグインフォルダに置かれている
> `create-link-plugin.md` は TerminalHub が配置・更新する。書き換えても
> 次の起動で内容が戻る（版が古いと嘘の仕様を読ませることになるため、
> 内容の新しさを優先している）。プラグイン本体の `.js` には触らない。

## 置き場所

| 種類 | 場所 |
|---|---|
| 自分で書くもの | `%LOCALAPPDATA%\TerminalHub\plugins\*.js` |
| 同梱のもの | アプリの `wwwroot\plugins\*.js`（更新で上書きされる） |
| この仕様書 | `%LOCALAPPDATA%\TerminalHub\plugins\create-link-plugin.md`（起動時に配置・更新される） |

自分のものはユーザー側に置くこと。アプリを更新しても消えず、リポジトリにも入らない
（社内 URL をうっかり公開リポジトリに入れずに済む）。

## 最小の例

```js
export default {
    id: 'youtube',
    pattern: /\b[A-Za-z0-9_-]{11}\b/g,
    url: (text) => `https://www.youtube.com/watch?v=${text}`
};
```

`export default` でオブジェクトを1つ返すだけ。ファイル名は自由。

## 書けるもの

| キー | 必須 | 内容 |
|---|---|---|
| `id` | ○ | 識別子。設定画面に出る。他と重複しないもの |
| `pattern` | △ | 検出する正規表現。**`g` フラグを必ず付ける**（無いものは読み込み時に弾かれる） |
| `url` | △ | `(text, ctx) => string \| null`。リンク先。`null` を返すとリンクにしない。`pattern` 方式では必須（`detect` 方式は hit 側に `url` を入れるため不要） |
| `accept` | | `({ text, before, after, line, ctx }) => boolean`。誤検出を弾く |
| `vars` | | `['baseUrl']` のような文字列配列。セッション設定に入力欄が出る |
| `detect` | | `(line, ctx) => [{ start, end, text, url }]`。`pattern` で表現できないとき用 |

`pattern` か `detect` のどちらかが要る。

### accept に渡るもの

`before` は**行頭から一致の直前まで全部**、`after` は**一致の直後から行末まで全部**
（数文字ではない）。なので前後を見るときは `/…$/` と `/^…/` のアンカー付きで書く。

```js
accept: ({ before, after }) => !/\[Image\s$/.test(before) && !/^-\d/.test(after)
```

### vars の値

宣言しただけで一度も入力していない変数は **`undefined`**（キーそのものが無い）。
一度入れてから空にすると **空文字**。両方あり得るので、読むときは
`(ctx.vars.baseUrl ?? '').trim()` のように畳んでから使う。空なら `null` を返して
リンクにしないのが行儀のいい書き方（設定し忘れが「壊れた」ではなく「まだ効かない」になる）。

### 重い処理を書かない

`url` / `accept` / `detect` は**表示される行ごと・有効なプラグインごとに**呼ばれる。
スクロール中も走るので、ここでの重い処理はそのままターミナルの重さになる。
正規表現と文字列操作の範囲に収めること（通信もストレージも触れない）。

## detect で書く

`pattern` の1発では表現できないとき（同じ行の複数トークンを組にする、
前後の文脈で URL を変える等）に使う。返すのは配列で、`url` は各要素が持つ。

```js
export default {
    id: 'log-level-docs',
    detect: (line) => {
        const hits = [];
        const re = /(ERROR|WARN)/g;
        let m;
        while ((m = re.exec(line)) !== null) {
            hits.push({
                start: m.index,
                end: m.index + m[0].length,
                text: m[0],
                url: `https://example.com/docs/logging#${m[0].toLowerCase()}`
            });
        }
        return hits;
    }
};
```

`start` / `end` は **`line` の文字位置**（JavaScript の文字列インデックス＝UTF-16 コード単位）。
`line` は ANSI エスケープを取り除いたあとの表示文字だけの行なので、色や装飾を数える必要はない。
全角文字が混じっていても、桁への変換はホスト側がやるのでプラグインは文字位置だけ考えればいい。
`url` が無い要素は捨てられる。範囲外の位置を返すと表示がずれるので、必ず `line` の中に収めること。

## ctx に入っているもの

```js
{
    sessionId,                        // セッションの GUID
    folderPath,                       // セッションの作業フォルダ
    terminalType,                     // 'ClaudeCode' | 'CodexCLI' | 'Terminal' など
    line,                             // 検出中の行のテキスト
    git: { originUrl, branch },       // git remote get-url origin の生の値とブランチ名
    vars: { ... }                     // セッション設定で入力した値（vars で宣言したもの）
}
```

`git.originUrl` は**解釈していない生の文字列**（`git@github.com:owner/repo.git` など）。
owner/repo の切り出しはプラグイン側でやる。GitHub 以外を使いたいときに
アプリ本体を触らずに済ませるため。

## 誤検出について

**素の正規表現は当たりすぎる。** ターミナルには短縮ハッシュ、base64 の断片、
ファイル名、トークンが日常的に流れる。たとえば YouTube の動画 ID は
「11 文字の英数字」でしかなく、そのまま当てると誤検出だらけになる。

対策は2つ。

**1. トークン自体を一意にする（推奨）**

`#123` のような一般的な形は他と衝突する。出力する側を
`CB#123` のように変えられるなら、そのほうが確実で安い。

**2. `accept` で文脈を見る**

```js
accept: ({ line }) => /youtu\.?be/i.test(line)
```

## 優先順位

同じ位置を複数のプラグインが取り合ったときは、**先に登録されたほうが勝つ**
（xterm のリンクプロバイダの仕様）。ユーザープラグインは同梱のものより先に登録されるので、
同梱の解釈を上書きできる。順序はセッション設定で変えられる。

`url()` が `null` を返した場合はその位置を占有しないので、
後続のプラグインや同梱の解釈にフォールバックする。

## 変数を使う例

案件ごとに URL が変わるものは `vars` で宣言し、セッション設定で値を入れる。

```js
export default {
    id: 'my-tracker',
    pattern: /\bCB#\d+\b/g,
    vars: ['baseUrl'],
    url: (text, ctx) => ctx.vars.baseUrl && `${ctx.vars.baseUrl}/items/${text.slice(3)}`
};
```

`baseUrl` が未入力なら `null` になり、リンクにならない。

## やれないこと

**URL を開くこと以外はできない。** 意図的にそうしてある。

- アプリの起動、ファイルを開く、コマンド実行はできない
- 通信（`fetch` 等）で内容を取ってくることはできない
- リンクを開く動作そのもの（新しいタブで開く / クリップボードにコピー）は
  アプリ側の設定に従う。プラグインからは選べない

プラグインは「この文字列は、この URL である」と申告するだけの純粋な関数。

## サンプル

すぐ使える例がリポジトリの [`docs/link-plugin-samples/`](link-plugin-samples/) にある
（`github-fixed` / `jira` / `backlog`）。プラグインフォルダにコピーして、
設定画面で変数を入れれば動く。自作の雛形にも使える。

## この仕様書の使い方

プラグインフォルダで Claude Code や Codex を動かし、「`create-link-plugin.md` を読んで
プラグインを作って」と頼めばそのまま自作できる。仕様も置き場所も同じフォルダにある。

## 反映のしかた

`.js` を保存したあと、セッション設定の「リンクプラグイン」を開き直す（開くたびに読み直す）。
一覧に出たらチェックで有効にし、同じ画面の「動作テスト」に1行貼れば、
何が引っかかってどのリンクになるかがその場で分かる（ターミナルに出るまで待たなくていい）。
すでに開いているターミナルへ反映するには、設定を保存するかブラウザのリロード。
うまく動かないときは DevTools のコンソールを見る。`import()` で読んでいるので、
Sources にファイルが出てブレークポイントも張れる。
